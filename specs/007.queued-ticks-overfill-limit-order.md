# 007 — Queued ticks overfill a paper LIMIT order

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

§1.1 A paper LIMIT order never fills for more than its own `amount`. However
many ticks cross it, and however they are queued, the sum of the fills equals
`amount` exactly once it is FILLED.

§1.2 Each fill moves the wallet by exactly the filled part: a BUY credits
`fill − fee` base and releases `fill × price` locked quote; a SELL credits
`fill × price − fee` quote and releases `fill` locked base. No release is larger
than what the order locked, so no locked balance goes negative.

§1.3 A tick that reaches an order with nothing left to fill (because an earlier
queued tick already filled it) does nothing: no order write, no wallet write, no
socket push.

§1.4 The order-row write is guarded in Mongo too. The `$inc` on `filledAmount`
only applies while `filledAmount + fill <= amount`. That way a stale RAM copy
can never push the persisted row over its size.

## §2 Evidence

- Prod `paperPositions`, 2026-11-20 to 2026-11-23: 15 FILLED LIMIT orders had
  `filledAmount > amount` (spot, partially filled across ticks). One example is
  `amount` 20885.89 with `filledAmount` 22679.77. Their over-release of locked
  balance is the `Balance update was not fully applied` / negative-locked
  finding on XAUT and MNT.
- Code path: `processTickerQueue` takes the order objects from RAM and calls
  `processLimitOrder(order, tick)` without awaiting it. `processLimitOrder` is
  serialised per `externalId` (`UpdateOrderMutex`), but it computes the fill
  from the `order` **argument**: `order.amount − order.filledAmount`. When a
  second tick is queued before the first one's `setOrder`, it carries the
  pre-fill object. After the first partial fill it fills the full remainder
  again. Its `$inc` and its wallet delta both apply.

## §3 Assumption (hypothesis)

The overfill comes from computing the remaining amount on the stale `order`
argument rather than the order state current inside the mutex
(`getOrderByExternalIdAndSymbol`, already read there as `inCurrent`).
Reading `filledAmount`/`filledQuoteAmount`/`fee` from `inCurrent` makes the
second queued tick see the first one's fill.

## Invariants

- `paper.limit-order-overfilled`: a FILLED paper LIMIT order whose
  `filledAmount` exceeds `amount` (relative 1e-6). Added to
  `specs/invariants/ledger.invariants.json` in the parent repo (observe mode).
