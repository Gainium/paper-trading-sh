# 002 — reduceOnly clamp refunds the wrong fee

Bug spec. Issue #632.

## 1. Definition

When a `reduceOnly` futures order is larger than the position it is closing,
`processFuturesPosition` clamps it: `order.amount` is cut down to
`current.positionAmt`, and the fee already charged for the units that were
clamped off is refunded.

### 1.1 Expected

After the clamp the order must be indistinguishable, fee-wise, from an order
that had been sent at the clamped size in the first place. Every fill in this
service charges

```
fee = (isCoinm ? (qty * contractSize) / price : qty * price) * feePerc
```

(`createOrder` for market fills, the resting-order fill loop for limit fills,
and the non-reduceOnly sibling branch, which recomputes it wholesale). So the
invariant after the clamp is

```
order.fee === (isCoinm ? (order.amount * contractSize) / order.price
                       : order.amount * order.price) * feePerc
```

and, since the clamp also sets `order.filledQuoteAmount = order.amount *
order.price`, on linear futures that reads simply
`order.fee === order.filledQuoteAmount * order.feePerc`.

Consequences that follow from it and are also part of "expected":

- `order.fee` is never negative. A fill cannot pay the trader.
- The wallet credit on close is `margin + grossPnl - fee` for that same fee.

### 1.2 Actual

The refund is not converted to notional the way the charge was.

- **Linear.** The refund subtracts a BASE quantity, `Math.abs(diff) * feePerc`,
  with no `* order.price`. It is short by a factor of `price`, so the order
  keeps the fee for units it never closed. For `price > 1` the trader is
  overcharged; for `price < 1` the refund is *larger* than it should be and
  `order.fee` can go negative, crediting the paper wallet.
- **Inverse (coin-m).** The refund subtracts a raw notional,
  `(Math.abs(diff) * contractSize) / order.price`, with no `* feePerc` at all —
  `1 / feePerc` (≈2000×) too large, which drives `order.fee` deeply negative.

The residual in both arms is
`order.fee - correct = clampedOffQty * feePerc * (price - 1)` (linear).

## 2. Evidence

### 2.1 Production state (read-only mongo, `gainium.paperPositions`)

Over the last 90 days, restricted to linear-futures `reduceOnly` FILLED paper
orders, comparing each order's stored `fee` against its own stored
`filledQuoteAmount * feePerc`:

| | |
|---|---|
| orders violating the invariant by >2% | **106** |
| distinct users | **21** |
| of those, overcharged (`price > 1`) | 36 — worst **1150×** (LTCUSDT, fee 0.195 vs 0.00017) |
| of those, undercharged (`price < 1`) | 70 |
| of those, ending with a **negative** fee | 41 — worst −94.40 (bybitLinear) |
| linear `reduceOnly` FILLED orders in the window | 746,436 |

This is not a shape mismatch in the query: for **106 of 106** rows the residual
`fee - filledQuoteAmount * feePerc` solves to a *positive* clamped-off quantity
under `resid = q * feePerc * (price - 1)`, and the quantities that come out are
clean order sizes (10.57 LTC, 336.26 ATOM, 0.216 ETH, 2180 AKE, 272 DOGE). A
formula error elsewhere would not produce residuals that factor exactly this
way. The most recent occurrence is 2026-09-04, i.e. it is still happening.

Negative fees by venue in the window: binanceUsdm 31 (7 users), bybitLinear 9
(4 users), hyperliquidLinear 1 (1 user) — all `reduceOnly: true`.

No coin-m occurrences in the window; the inverse arm is wrong by inspection and
by the same invariant, but is not observed in production state.

### 2.2 Executing the shipped code

`src/order/reduce-only-clamp.spec.ts` drives the real (private)
`processFuturesPosition` off the prototype with stubbed models. It reproduces
all three shapes — see §4.

## 3. Assumption (hypothesis)

The whole defect is the single expression at the top of the
`diff <= 0 && order.reduceOnly` branch in
`src/order/order.service.ts`. Both ternary arms omit part of the conversion the
matching charge applied: the linear arm omits `* order.price`, the coin-m arm
omits `* feePerc`. Nothing else on that branch is wrong — the amount clamp, the
profit calculation and the wallet delta all consume `order.fee` and are correct
once it is.

Plus, for each: `fee >= 0`, the amount is clamped to the position size, and the
wallet credit equals `margin + grossPnl - fee` for the corrected fee.

## 5. Out of scope

- Historic paper wallets already skewed by this. No backfill is proposed; the
  amounts are small (worst single order −94.40 quote) and rewriting a user's
  paper ledger is a larger decision than this fix.
- `isFutures`/`isCoinm` not listing `bybitLinear`/`bybitInverse` under those
  enum *keys* — noticed while querying, unrelated to this branch, not touched.
