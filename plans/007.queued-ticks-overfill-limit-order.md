# Plan 007 — Queued ticks overfill a paper LIMIT order

Spec: `specs/007.queued-ticks-overfill-limit-order.md`.

## Build order

1. Red tests: `src/order/queued-tick-overfill.spec.ts` drives the real
   `processTickerQueue` → `processLimitOrder` (mutexes included) with a
   Mongo-faithful order row.
2. `processLimitOrder` (`src/order/order.service.ts`):
   - after the existing `inCurrent` check, size the fill from `inCurrent`
     (the RAM order as it stands inside the per-order mutex), not from the
     argument captured when the tick was queued (§3);
   - clamp the fill to `max(0, amount − filledAmount)` and return when it is
     0 (§1.3);
   - guard the `updateOne` with `filledAmount <= amount − fill` (`fillGuard`,
     1e-12 relative slack for float error only) on both the SELL and BUY
     branches (§1.4);
   - move the wallet only after the guarded write matched, instead of in
     parallel with it, so a refused fill never pays out (§1.2);
   - a write that matched nothing goes to `limitFillRefused`. If the row is
     gone, the existing `rowIsGone` eviction applies. If the row still exists,
     the guard refused the fill: RAM is re-synced from the row and nothing else
     happens (no push, no wallet, no futures position).
3. Parent repo: invariant `paper.limit-order-overfilled` (observe) in
   `specs/invariants/ledger.invariants.json`.

JIT extraction tier: none. The change stays inside the two existing fill
branches. Extracting the duplicated SELL/BUY fill into a pure function is
the obvious next tier, but it would rewrite the whole method for a
three-line root cause.

## Blast Radius

1. Call sites: `processLimitOrder` is called only from `processTickerQueue`.
   `limitFillRefused` and `fillGuard` are new and private.
2. `core/` = paper-trading-sh: shared by every paper-trading deployment
   (cloud + self-hosted). No exported type, REST shape or socket event
   changes.
3. OWNS/EMITS: the socket `order` push is unchanged in shape. It is now
   skipped for a refused fill, and it is sent before the wallet update instead
   of in parallel with it (same order of events as before for the client:
   the order event, then `outboundAccountInfo` from updateBalance).
   The `paperPositions` rows are unchanged in shape.
4. Other tests: whole mocha suite (`npm test`) stays green.
