# 005 — same-tick futures fills open duplicate positions

Bug spec.

## 1. Definition

### 1.1 Expected

A user holds at most one open paper futures position per symbol (per side in
hedge mode). Two fills that add to that position — however close together they
arrive — end up in that one position: its size is the sum of the fills and its
entry price their weighted average, exactly as a real exchange books them.

### 1.2 Unchanged

Fills for different users, or for different symbols, are independent and keep
producing their own positions.

## 2. Evidence

Production state (read-only): two `LIMIT` entry orders for one user and symbol,
resting at the same price, are both marked `FILLED` in the same millisecond, and
two `paperFutures` documents for that user, symbol and side are created in one
later millisecond with consecutive `_id`s, identical size and entry price, both
`NEW`. The order fills carry no error and the service logs nothing for them —
the duplicate is silent. The invariant `paper.duplicate-open-position`
(`specs/invariants/ledger.invariants.json` in the parent repo) is what found it.

## 3. Assumption (root cause hypothesis)

`processTickerQueue` calls `processLimitOrder` for every crossed order on a tick
without awaiting it, and `processLimitOrder` is serialised only per order
(`UpdateOrderMutex` keyed on `externalId`). Each fill reaches
`processFuturesPosition`, which awaits the hedge-mode lookup, finds the position
in memory, and on a miss awaits `positionModel.create` before registering the
new position. Nothing serialises that read-then-create across orders, so two
fills inside the window both miss and both create. The market path
(`processMarketOrder`) and the liquidation path (`closeFuturePosition` →
`createOrder`) funnel into the same function and share the window.

`same-tick-open.spec.ts` fails with `positionModel.create ran twice` before the
fix — the failure this assumption predicts.

## 4. Fix

Serialise `processFuturesPosition` with its own `IdMutex` keyed on user and
symbol. The exchange is left out of the key because the in-memory lookup it
protects does not filter on exchange either. Not `commonMutex`:
`lockLeverage` / `unLockLeverage` take that mutex on a user-symbol key and are
called from inside `processFuturesPosition`.

## Invariants

Already covered by `paper.duplicate-open-position` (parent repo,
`specs/invariants/ledger.invariants.json`); no new invariant.
